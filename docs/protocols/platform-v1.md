# Platform protocol `platform-v1`

Status: draft — frozen when the first cohort is published  
Schema: `schema_version: 2`  
Category: `platform`  
Profiles: `standard`

This document fixes the meaning of reports carrying
`protocol_version: "platform-v1"`. Until the first cohort lands in
`data/results/` the method may still be corrected; from then on a change needs
a new protocol identifier and existing reports are never reinterpreted.

## Why this suite exists

Two machines with the same CPU can differ several times over in what the layer
underneath a workload costs: a system call that leaves the guest, a page fault
resolved by a userspace kernel, a process started through a sandbox shim, a
vCPU that is descheduled without the guest being told. A throughput benchmark
that stays inside one process sees none of it.

The suite is written for Linux. On other systems it runs the tests that apply
and says in the result notes which probes are missing.

## Standard profile

| Test | Metric | Unit | Direction |
|---|---|---|---|
| kernel | `syscall` | ns | lower |

| kernel | `clock_read` | ns | lower |
| spawn | `process_spawn_p50` | us | lower |
| spawn | `process_spawn_p99` | us | lower |
| files | `file_create` | ops/s | higher |
| files | `file_read` | ops/s | higher |
| files | `file_delete` | ops/s | higher |
| stall | `lost_time` | % | lower |
| stall | `longest_stall` | ms | lower |
| stall | `stall_rate` | per core-minute | lower |
| stall | `reported_steal` | % | lower |
| stall | `runqueue_wait` | % | lower |

### kernel

Each probe runs on one thread for 1.5 seconds.

- `syscall` is the mean cost of `getppid(2)`, which does no work in the
  kernel: the price of the boundary itself.
- `pipe_roundtrip` is the mean time of one ping-pong between two threads that
  block in `read(2)` on a pipe until the other writes a byte. A round trip is
  two thread wake-ups and four system calls.
- `memory_first_touch` maps 64 MiB of anonymous memory and writes one byte to
  every page, repeatedly. Only the touching is timed. Transparent huge pages
  are declined with `MADV_NOHUGEPAGE` so the result does not depend on a
  distribution default. The page size is recorded in the notes; the metric is
  in bytes per second so page sizes compare.
- `clock_read` is the mean cost of one monotonic clock read. The active kernel
  clocksource is recorded in the notes.

`memory_first_touch` reuses pages the guest kernel has already been given. It
does not show how fast the host backs memory the guest has never used.

### spawn

`spawn` writes a static helper into the scratch directory and starts it back
to back for three seconds with `fork`/`exec`, waiting for each exit. The helper
is one ELF header, one program header and three instructions that call
`exit(0)` — 129 bytes on amd64, 132 on arm64, generated by
`internal/tests/platform/exithelper.go`. Nothing but the kernel's process
lifecycle is timed.

Starting a real program instead would mostly measure that program: this
binary spends about 4.5 ms initialising its libraries, against roughly 0.1 ms
for the process start itself.

The scratch directory must allow execution; pass `--dir` when the default is
mounted `noexec`.

### files

`files` creates 10,000 files of 4,096 bytes in one directory, reads them back
in a fixed shuffled order, then deletes them in that order. Each phase is
timed separately. Every file carries its own index so no two have the same
content, and every read is checked. Nothing is synced: this is the shape of a
package install or a checkout, bound by filesystem metadata.

### stall

Every usable CPU runs a thread that reads the clock in a tight loop for ten
seconds. A jump between two consecutive reads is time the thread did not run.

- `lost_time` is the sum of gaps of 100 µs or more, as a share of the total
  thread time.
- `longest_stall` is the longest single gap.
- `stall_rate` counts gaps of 1 ms or more per core-minute.
- `reported_steal` is the steal share from `/proc/stat` over the same window:
  what the hypervisor chose to tell the guest.
- `runqueue_wait` is the time the process's threads spent runnable but waiting
  in the guest's own scheduler, from `/proc/self/task/*/schedstat`, as a share
  of the total thread time.

Reading them together:

- `lost_time` near zero: the threads ran undisturbed.
- `lost_time` about equal to `runqueue_wait`: the guest's own scheduler ran
  something else. On a virtual machine that is other activity inside the
  guest. In a container it is the host kernel, so a CPU quota enforced by the
  container runtime appears here — and never in `reported_steal`.
- `lost_time` well above `runqueue_wait`: the time was taken below the guest.
  This is hypervisor steal, whether or not `reported_steal` admits it.

`runqueue_wait` also counts waits shorter than 100 µs and the runtime's helper
threads, so it can slightly exceed `lost_time`.

The detector was checked against a known answer: eight spinning threads under
a two-CPU container quota must lose 75% of their time. It reported 74.98%
`lost_time` while `reported_steal` read 0.12%.

"Usable CPUs" is the Go runtime's parallelism (`GOMAXPROCS`): the logical CPUs
of the machine, capped by a container CPU quota where one applies.

## The toolchain is part of the method

Every report records the Go release that built the binary as
`environment.go_version`; a cohort must come from one toolchain. `--quick`
shortens every probe and is never ranked.

## Cohort contract

A standard cohort follows the compute design: ten independently provisioned
fresh samples, three successful repeats each, one binary. The validator checks
report structure, campaign coordinates and metric definitions across the
cohort. It defines no composite ranking for this category yet; published
cohorts are shown as measured, without an index.

A fresh instance is rarely idle: first-boot package updates can occupy a core
for minutes. `runqueue_wait` exists so that such guest activity is visible in
the report instead of being read as contention on the host.
